Module 01 · Foundations

What AI actually is — and isn't.

Get the mental model right before touching the tool. Wrong mental models create wrong expectations, which create wrong outcomes.

A large language model is a pattern-completing machine. It has read a very large fraction of the text on the internet, and it is very good at predicting what word comes next given what it has seen so far. That's it. Every impressive thing you'll see it do is an emergent consequence of doing that one thing at massive scale.

The four false mental models to unlearn

What people assumeWhat's actually true
"It's a search engine that phrases nicely."It does not look up anything by default. It generates text that sounds like the answer, drawn from patterns it saw during training. This is why it invents.
"It knows my codebase."It knows only what's in its context window right now. If you didn't paste your code or point Claude Code at your repo, it's guessing based on general Go idioms.
"If it sounds confident, it's right."Confidence and correctness are unrelated. The model sounds confident because well-written text sounds confident. Verify separately.
"It reasons like a person."It produces text that resembles reasoning. Sometimes this is functionally equivalent to reasoning. Sometimes it produces text that looks like reasoning but arrives at a wrong conclusion. You cannot tell from the output alone.

What it is genuinely great at

  • Reading unfamiliar code fast. Paste a 300-line Go file, ask "what does this do?", get a summary a senior would take 15 minutes to write.
  • Translation between forms. Turn a stack trace into an explanation. Turn a JSON schema into a Go struct. Turn a ticket description into a test plan.
  • Boilerplate at scale. Ten similar functions? One prompt, ten functions, verified by hand.
  • Second opinions. "Here's my approach — what am I missing?" is one of the most valuable prompts an experienced engineer can use.
  • Explaining errors in plain language. Especially useful when your team's Go beginner meets a nil-pointer panic at 4pm on a Friday.

What it's still bad at

  • Anything requiring live information. Current stock price, today's flight availability, your production database contents.
  • Long chains of exact arithmetic. It will confidently compute 174 × 293 = 51,082 (correct: 50,982). Use a calculator or code for math.
  • Novel security bugs. It knows OWASP top ten patterns; it doesn't know the specific way your payment gateway's HMAC verification is subtly wrong.
  • Recency. Its knowledge has a cutoff date. Newer library versions, freshly-published CVEs, this week's news — treat as unknown.
  • Deep debugging of concurrency bugs. Race conditions in production Go code need a human plus profiler.
The one line to remember

AI is a very fast, very well-read, very confident junior colleague who never gets tired but occasionally makes things up. Treat every claim it makes the way you'd treat an unreviewed PR from a new hire.

Module 02 · The core skill

The one skill — writing a prompt that works.

If you master this and nothing else in this workbook, you'll get 80% of the value. A good prompt is the whole game.

A prompt is not a Google query. It's a brief to a colleague who has just walked into the room and knows nothing about you, your project, your yesterday, or your goal. Everything they need must be in what you say.

The anatomy of a prompt that works

Every effective prompt has some combination of these five parts. Miss the ones you need and the output degrades sharply.

PartWhat it doesExample
ContextGrounds the model in your situation"I'm working on tk-flight-jazeera, Go 1.22, on feature/v4.5."
TaskThe one specific thing you want done"Add a GET /health endpoint that returns the last successful upstream call time."
ConstraintsRules the answer must obey"Don't touch go.mod. Use zerolog. Match the existing handler pattern in main.go."
FormatHow you want the answer shaped"Give me the code diff only, no prose explanation."
ExamplesShow what "good" looks like"Similar to the /ready endpoint in tk-hotel-main line 84."

Bad → good, using our own stack

Example 1 — asking about an error.

Bad
fix this go error
Good
I'm getting this panic on tk-flight-jazeera startup, on feature/v4.5, after we removed the tk-logger replace directive yesterday. [paste full stack trace here] What's the most likely cause? Explain your reasoning in one paragraph, then propose a specific one-line fix.

The bad one gets a generic tutorial on Go errors. The good one gets the actual diagnosis, because Claude now knows the repo, the branch, the recent change, and what shape of answer you want.

Example 2 — asking for code.

Bad
write a hotel search endpoint
Good
In tk-hotel-main (Go, micro/go-micro/v2), add a POST /hotels/nearby endpoint that takes {lat, lng, radius_km} and queries our Typesense at localhost:8108 with a geo_distance filter. Return the same response shape as the existing /hotels/search response (see handlers/search.go). If Typesense returns no results, respond with an empty array, not an error. Match the existing handler pattern including zerolog logging and the standard error envelope.

The bad one gets a made-up endpoint using libraries you don't use. The good one produces something that actually fits your codebase.

Example 3 — code review.

Bad
review my PR
Good
Review this PR against three specific questions: 1. Does it silently swallow any error? 2. Does it change any shared-library version in go.mod? 3. Does it introduce a new external network call? Ignore code style. Flag only the three things above. [paste the diff]

Focused review beats general review. The bad prompt gets you 40 style nits. The good one gets you the 3 things that actually break production.

Example 4 — generating tests.

Bad
test this function
Good
Generate table-driven Go tests for this function. Cover four cases: - happy path with a well-formed input - empty input string - input containing an Arabic name with a hamza character (ء) - upstream Jazeera API returns HTTP 429 Match the existing test style in this repo — see any *_test.go file. Use testify/require. No mocks; use httptest.Server for the upstream case. [paste function]

Naming the edge cases matters more than any technique. If you don't list them, Claude picks generic ones and misses the Arabic/hamza edge case that will actually bite you.

Example 5 — explaining code.

Bad
explain this code
Good
In one paragraph, explain what this function does. Assume the reader knows Go but has never seen tk-flight-jazeera. Don't repeat what the function name already says. Focus on the "why", especially around any non-obvious workaround. [paste function]

Without constraints Claude gives you a line-by-line comment stream that's useless. With them, you get the paragraph you actually needed.

Five universal patterns that improve most prompts

  1. Say who's asking and what you already know. "I'm a backend dev familiar with Go but new to Typesense" changes the answer completely.
  2. Say what a good answer looks like. "Under 300 words." "A diff." "A bullet list." "A step-by-step plan."
  3. Give a real example, not an abstract description. "Match this style: [paste 5 lines of the existing style]" beats "match our style."
  4. Name the edge cases you care about. Claude will not think of the RTL Arabic edge case unless you say Arabic.
  5. Ask it to think before answering, for hard questions. "Think through the failure modes before proposing a fix" produces measurably better answers on complex debugging.
Anti-pattern to catch yourself doing

Chaining lots of "and also make it…" clauses in one prompt. Ten constraints in one prompt gets you an answer that satisfies five and quietly ignores five. Break into two prompts.

Cheat sheet

Prompt patterns to memorize

Grounding

  • "I'm working on [repo], [language], [branch]."
  • "Assume the reader knows X but not Y."
  • "Here's the file I care about: [paste]"
  • "Similar to how X handles Y in [reference]"

Shape

  • "Under N words / one paragraph"
  • "Diff only / bullet list / step-by-step"
  • "Explain your reasoning, then answer"
  • "Rank by probability / severity / effort"

Focus

  • "Flag only these three things"
  • "Ignore style, look at correctness"
  • "Focus on the why, not the what"
  • "Consider these edge cases: [list]"

Quality boosters

  • "Think through failure modes first"
  • "What am I not asking that I should?"
  • "Give three options with tradeoffs"
  • "If uncertain, say so explicitly"
Module 03 · The tool

Driving Claude Code without getting lost.

Claude Code is the interface. Learn its five key concepts and you can do 90% of your daily AI-assisted work in it.

Claude Code is not a chat window. It's a working environment where the model can read your files, run commands, edit code, and remember context across sessions. Think of it as a very literate pair-programmer that shares your terminal.

The five key concepts

ConceptWhat it isWhen you use it
SessionA conversation with Claude that can span hours. It remembers what you've done during it.Every task starts a session. One session per topic; new task = new session.
MemoryLong-term notes Claude writes about you, your projects, your preferences. Persists across sessions.Automatic. Read what it saved in ~/.claude/projects/…/memory/. Ask "what do you remember about me?"
ToolsActions Claude can take: Read a file, run Bash, edit code, fetch a URL.Automatic — Claude picks the right tool. You approve them the first time.
AgentsSpecialized sub-Claudes for focused jobs — Explore, Plan, code-reviewer.When one task is large or benefits from a fresh context.
SkillsPre-built workflows — /code-review, /schedule, /run.Invoked with a slash command. Learn the ones for your role.

The five daily workflows you'll use most

  1. "Explain this code to me." Open Claude Code in a repo. "Read handlers/search.go and explain in three sentences what this handler does, then list any surprising behaviors."
  2. "Fix this specific bug." Paste the stack trace + describe recent context. Let Claude propose the fix. You review before it edits.
  3. "Add this small feature." Ground it in an existing similar feature. Ask for the diff. Review and iterate before merging.
  4. "Review this PR." Run /code-review or ask Claude directly with the diff. Read its findings, verify each one.
  5. "Search across the whole codebase." "Find every place we call config.Get(\"hosts\", \"cache\")." Faster than grep for cross-repo questions.
The habit worth building

Start every new task by saying out loud what you want in one sentence, then paste the sentence to Claude. If you can't say it in one sentence, the task is too big — split it first.

What NOT to do in Claude Code

  • Don't let it run a destructive command without reading it first. rm -rf, git reset --hard, DROP TABLE — always check before approving.
  • Don't paste live production data — logs, database rows, request bodies containing customer info. See Module 4.
  • Don't ask it to edit files you haven't opened yourself first. You need to know the current state before it starts changing things.
  • Don't chain 15 tasks in one prompt. One task at a time. Verify each step.
Cheat sheet

Claude Code one-pager

Useful slash commands

  • /help — command reference
  • /code-review — review the current diff
  • /run — start & verify the project
  • /security-review — audit the current change
  • /plan — design before you code

When to spawn an agent

  • Explore — cross-repo search, "where is X used"
  • Plan — non-trivial feature design
  • code-reviewer — heavy PR review
  • general-purpose — anything complex & multi-step

Approve carefully

  • Any rm, DROP, git reset
  • Any push to a remote branch
  • Any deploy or restart command
  • Any edit to files outside the current repo

Approve freely

  • File reads
  • Grep / find in the repo
  • Read-only git commands (status, log, diff)
  • Edits to files you've been discussing

Module 04 · Security

Security — what never gets pasted.

One paste of a wrong file to a public AI can leak customer data. Learn the rules so hard that you can't accidentally violate them.

The default assumption: anything you send to any AI tool may be logged, may be reviewed by a human, may be used to train a future model, may be subpoenaed, and may leak. That's the risk model. Everything below flows from it.

The never-paste list

CategoryExamplesEven if…
Production credentialsDB passwords, API keys, JWT signing secrets, OAuth tokens, SSH private keys, service accountsThey're "old". They're "dev". You're going to rotate them.
Customer PIIPassport numbers, national IDs, addresses, phone numbers, real names tied to bookings, email + booking togetherYou anonymize the ID. Combination of "safe" fields often re-identifies.
Booking & payment dataFull PNRs, card numbers (even masked), CVV, IBAN, bank account, transaction refsThe card is expired. It's your own card. The transaction is old.
Real logs with real dataServer logs containing user emails, session IDs, request IDs tied to real usersYou "grep out the sensitive lines". You usually miss some.
Internal URLs & hostnamesProduction VPN hosts, internal IPs, service URLs with embedded tokensThey're behind a firewall. Firewalls don't help if the URL itself is a secret.
Client-privileged docsContracts, NDAs, internal financials, employee data, unreleased pricingYou have permission "to read them". Permission to read ≠ permission to redistribute.

The always-safe list

CategoryExamples
Source code (except embedded secrets)Handlers, models, config schemas — as long as you scrub any hard-coded secrets
Sanitized stack tracesPanics with generic values; strip anything customer-specific
Architecture questions"How should we structure caching between tk-hotel-main and Typesense?" — abstract
Anonymized test dataFake names, fake emails (test@example.com), obviously-fake card numbers
Public library documentation questions"How does micro/go-micro/v2 config.Get resolve nested keys?"

The sanitization habit

Before pasting any real file or log, run through this five-second check:

  1. Does this contain a value that looks like a password, key, or token? (High-entropy strings, base64 blobs, hex strings.) → Redact or refuse.
  2. Does this contain a real person's identifying data? → Replace with fake.
  3. Does this contain a URL or hostname that isn't public? → Replace with placeholder.
  4. Is this a customer's actual booking, payment, or transaction record? → Never paste.
  5. Would you post this in a public Slack channel? If no, don't paste.
The Tathkarah rule

Assume every AI-facing conversation could be attached to an exhibit in a compliance audit. If you wouldn't want a regulator reading it, sanitize it.

Sanitization by example

Module 05 · Verification

Verifying — catching a confident wrong answer.

Every AI answer is a hypothesis until you verify it. Learn the three ways to verify and the red flags that mean "verify this one especially carefully".

The single biggest failure mode of AI-assisted work is accepting an answer that sounds right and isn't. This module teaches you to see it coming.

Why models get things confidently wrong

The model is trained to produce plausible text. Plausibility and truth are correlated but not the same. When the model has no direct memory of the answer, it will smoothly interpolate — producing text that reads as authoritative but is fabricated. This is not lying; it's the model doing exactly what it was trained to do.

The three verification patterns

  1. Run it. If it's code, execute it. If it's a command, try it in dev first. If it's a SQL query, run it against a copy.
  2. Look it up. If it cites a library function, check the library's documentation. If it cites a Go language feature, check the Go release notes. If it names a file or line number, open the file.
  3. Ask it again, differently. Phrase the same question a different way. If the two answers disagree, at least one is wrong; sometimes both.

Red-flag phrases that mean "verify harder"

When Claude says…What it often meansWhat to do
"I believe…"Uncertain — it's guessingVerify directly.
"Typically…" / "Usually…"General pattern, may not apply to your specific caseCheck for your specific version/config.
"You should…"Reasonable advice, not verified factConfirm before committing.
Confident specific version numbers you didn't provideFabricatedCross-check against your actual go.mod or pubspec.yaml.
Referenced file paths you didn't shareGuessed based on conventionAsk Claude to grep for it before trusting.
Very long, very detailed answers to short questionsMay be padding with plausibilityAsk for a shorter version to see what survives.

A real Tathkarah example — the tk-logger diagnosis

Last week we hit a checksum mismatch error building tk-flight-jazeera. Here's how the AI-assisted diagnosis went, and where verification mattered:

  1. Claude's first guess — "the go.sum has a stale hash, delete the tk-logger lines and re-tidy." → Verified by running it. Didn't fully work — surfaced a deeper issue.
  2. Second observation — "the tk-logger v1.0.1 tag on GitHub still points at the pre-migration commit." → Verified by hitting the GitHub API directly. Confirmed true.
  3. Real root cause — "the replace directive in go.mod forces the tk-logger version to the broken tag." → Verified by reading the go.mod and comparing to feature/v4. Confirmed.
  4. Proposed fix — remove the replace directive. Verified by running go build ./... — clean.

Notice: every step involved a verification. Claude's first guess was partially wrong; the diagnosis got right by running things and reading real state, not by trusting the first answer.

The habit worth building

After Claude gives you an answer, say out loud: "How would I know if this is wrong?" If you don't have an answer to that question, don't trust the AI answer yet.

Module 06 · The rhythm

The practice loop — after this workbook.

Skills learned in a workbook decay in weeks unless practiced. Here's the rhythm to keep.

Three standing forums, forever

ForumCadenceWhat happens
AI clinicWeekly · 30 minOne team member shares a prompt or workflow that saved them time this week. Others copy it.
Failure post-mortemMonthly · 45 minCases where AI got it wrong. What happened, how caught, what to do next time.
Tools refreshQuarterly · 90 minWhat's new, what's worth adopting, what's the team already doing better than the tooling assumes.

Your personal daily loop

  • At the start of every task, ask: "would AI help here?" Sometimes the answer is no. Getting good at the answer is the skill.
  • When AI produces something you'll ship, verify at least one specific claim in the output before merging.
  • When AI gets something wrong, write down what happened. Not to blame — to notice patterns.
Graduation criteria

You have finished this workbook when you can (1) write a five-part prompt without thinking about it, (2) name the three verification patterns and use one on every non-trivial AI output, and (3) sanitize a real log line without checking the never-paste table.
