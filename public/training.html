Introduction

18 backend services, two Flutter apps, supplier integrations (Jazeera, RezLive), the alpha environment and an AWS estate — maintained by a small team. AI assistants are a force multiplier on exactly this kind of surface area.

Velocity

Guardrails

Second-opinion review on a diff, targeted refactors, dead-code cleanup.

Our toolkit: Claude Code is an agent in your repo, not a chat window — it reads the codebase, edits files, runs tests and works with git. Each repo’s CLAUDE.md is its onboarding doc; keep it current. Company workspace accounts only — personal or free AI accounts never touch Tathkarah code.

Fundamentals

How it fails on code

Hallucinated APIs

Invents methods, fields and endpoints that don’t exist — especially on niche or internal APIs like our supplier integrations.

Version drift

Suggests APIs from an older major of a library, or deprecated Flutter widgets — its training data lags our package.json and pubspec.yaml.

Plausible-but-wrong

Compiles, reads clean, passes the happy path — then breaks on edge cases: timezones, currency rounding, double bookings.

Security naivety

Will happily concatenate SQL, log PII, or skip auth checks unless your prompt and review demand otherwise.

What that looks like in our stack

Invented supplier fields

Ask about the Jazeera ServiceBundlesInfo response and it may invent fields that aren’t in the payload. Source of truth: the real API response and our integration notes — paste them in.

Wrong library era

Suggests a better-sqlite3 or Flutter API from two majors ago. Check the installed version in package.json / pubspec.yaml and say it in the prompt.

Confident migration, silent data loss

A clean-looking ALTER TABLE that renames without backfill. Migrations for Console-DB never run anywhere real without review, backup and an alpha pass.

The rule: “looks right” is not done. Done = failing test reproduced → fix → tests pass → you reviewed every line → it runs in alpha.

Session 2

Working with the agent

The #1 differentiator between engineers who get value from AI and those who don’t is the quality of context they provide.

Point it at the code

Run it inside the repo. Name services and files: “in tk-hotel-main, the booking handler” beats “my API”.

Paste the real evidence

The exact error, full stack trace, failing request/response, expected behaviour. Sanitise customer data first.

Feed it the contract

Supplier API docs, a real (sanitised) Jazeera or RezLive payload, the ticket text — it can’t guess our integrations.

Maintain CLAUDE.md

Stack, run commands, conventions, gotchas per repo. Ten minutes of upkeep pays off every single session.

Anatomy of a good dev prompt

  1. GoalWhat outcome, exactly?“Fix the 500 on POST /bookings when a guest books two rooms”
  2. ContextCode, errors, payloads“Stack trace below; booking flow is mock → rezlive → hotel-main”
  3. ConstraintsStack, style, versions“Node 25, our existing error-handler pattern; don’t touch the rezlive client”
  4. Definition of doneHow we’ll know it works“Write a failing test first; all tests green; no new dependencies”
  5. Scope limitWhat NOT to do“No refactors outside this handler; no schema changes”

Same bug, two prompts

Weak
fix the bug in hotel booking

It guesses which bug, guesses the design, touches files you didn’t want touched — and you spend the afternoon reviewing a sprawling diff.

Strong
In tk-hotel-main, POST /bookings returns 500 when a
guest books 2 rooms in one order. Stack trace below.
Expected: one booking with two room entries.
Reproduce with a failing integration test first, then
fix. Don't modify the rezlive client. Run the full
suite when done.

60 seconds of prompt-writing buys you a small, reviewable, tested diff.

Plan before big changes

For multi-file work, ask for a plan first and correct it before any code is written — cheaper than reviewing wrong code.

Iterate on the diff

“Extract that into the service layer”, “handle the null supplier case”, “match our error-handler pattern” — refine, don’t restart.

Make it prove it

“Write the failing test first.” “Run the suite.” “Show me the output.” Evidence beats confidence, every time.

Keep diffs small

One concern per session. A 1,500-line AI diff isn’t productivity — it’s an unreviewable liability.

Guardrails

Never in a prompt

ClassWhat it coversRule
GREENOur source code (per repo policy) · sanitised stack traces & logs · redacted payloads (<NAME>, <PNR>) · fixtures & dummy data · public docsUse freely in approved tools
AMBERReal logs and payloads (may hide passenger names, phones, PNRs) · internal docs · incident threadsStrip identifiers first
REDAPI keys, tokens, passwords, .env, connection strings, AWS/SSH credentials · production DB dumps · customer PII (passports, cards, contact lists)Never. Pasted by mistake? Rotate the key and tell your lead the same day

Danger zones — AI drafts, seniors approve

Payments

tk-payment-core and anything touching money movement or refunds — full senior review, no exceptions.

DB migrations

Schema changes on Console-DB and service DBs: review + backup + run in alpha before anywhere real.

Auth & sessions

Login, tokens, permissions, agent access levels — subtle AI mistakes here become security incidents.

Deploy & infra

The GitHub→alpha pipeline, runner config, AWS changes — a wrong script takes down every environment at once.

In these areas AI is a drafting tool only — a named senior engineer signs off before merge, and nothing auto-runs against real systems.

Wrap-up

Five rules to remember

  1. You own what you mergeSame review bar, tests pass, you understand every line. “The AI wrote it” is never an explanation.
  2. No secrets, no customer dataKeys, tokens, .env, prod dumps, passenger PII — never in a prompt. Fixtures and redacted samples instead.
  3. Verify against the source of truthReal API contracts, installed versions, actual runtime behaviour. Run the code; don’t trust the prose.
  4. Small, tested, reviewable stepsFailing test first, one concern per diff. Never merge a diff too big to review properly.
  5. Danger zones get senior eyesPayments, migrations, auth, deploy/infra — AI drafts, a named senior approves.
